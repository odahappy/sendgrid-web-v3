# 自定义预热任务

预热系统是独立任务类型。原有“任务管理”的固定 30 天随机数量规则仍保留，但两类任务现在从同一个收件人池取件。标签、API 通道和代理在同一个“标签 / API 通道 / 代理”页面管理。

## 建立收件人池与名单筛选

从“收件人”页面上传 TXT/CSV 到唯一的收件人池；一个标签下的同一邮箱只计入一次可用库存。固定 30 天任务直接使用对应标签的可用地址。预热任务可使用该标签的整个池，也可选择具名名单作为筛选条件。如需建立具名名单，在“预热系统 → 上传具名名单”导入 TXT/CSV，并填写名单名称、许可来源和许可取得时间；新地址进入同一个池，名单只记录成员关系，不建立第二个物理库存。同一邮箱即使属于多个名单，也不会在同一个任务中重复发送。

只使用已明确同意接收相应邮件的收件人。上传名单和新建任务时填写或确认许可信息；退订、投诉、退信事件记录中的地址会被排除。停用具名名单后，该名单独有的地址在统一池内显示为“不可用”，也不能被新计划选中；独立导入普通池的地址即使同时属于该名单，仍按普通池的许可和退订状态判断。

## 上传 HTML 模板

在“HTML 模板”页面上传时，先填写邮件主题和发件人显示名称；这两个值会分别绑定到本批上传的**每个 HTML 文件**。上传后可逐个编辑文件的绑定值，因此同一模板组中的文件可以使用不同的主题和名称。任务选择模板组后，新生成的每封邮件使用其选中 HTML 文件的主题和发件人名称。发件人邮箱、API Key 和代理仍来自任务选择的 API 通道。主题可使用系统支持的模板变量，例如 `{{code8}}`。

旧版 HTML 文件没有绑定值时，继续使用任务原有的主题和通道发件人名称。已生成计划中的主题、发件人名称和 HTML 文件引用作为发送快照保留；修改模板绑定信息不会回写旧计划。

## 新建并启动

1. 在“预热系统”点击“新建预热任务”，选择标签、已启用的通道、模板组以及收件人池或具名名单筛选。
2. 填写天数（1–90）；页面立即生成等量的**空白**每日数量输入框。逐天填写非负整数，填 0 表示当天不发送；总数应为 1–100000 封。
3. 选择“系统自动安排”或输入固定间隔秒数（1–86399）。手动模式第 n 封相对当天起点的理论时间为 `(n−1)×间隔`；最后一封必须落在该天的 24 小时内。
4. 保存后任务处于草稿状态。首次点击“启动”时，服务器才冻结开始时刻 T0、核验通道自然日限额和筛选后的单池库存，并一次性预留收件人和生成发送计划。库存或容量不足会提示错误，不会留下部分计划。

第 k 天的窗口从 `T0+(k−1)×24小时` 到 `T0+k×24小时`（不含结束时刻）。自动模式把当天 n 封均匀排在窗口内，理论间隔为 `86400÷n` 秒；手动模式按填写的秒数排列。当天发送完毕后，下一天的首封只会在下一窗口开始时到期。页面将 UTC 时间戳换算成浏览器本地时间显示；夏令时变化不会改变真实的 24 小时边界。

**发送时间是最早可发时间**。worker 轮询、网络耗时、暂停、服务停机或通道限额可能造成延迟。系统按实际上一次发送完成后的时间维持至少所设间隔；若无法在本日窗口内完成，剩余项标记“错过”，不会突发补发或占用下一天的配额。手动间隔设得接近 24 小时边界时，正常的轮询延迟也可能导致末封错过。通道原有的“每日限额”按服务器自然日计算，和任务的滚动 24 小时额度同时生效。

## 状态与人工核销

“已发”表示 SendGrid API 接受请求，并不表示邮件已送达；送达、退订与投诉应以已配置的 Event Webhook 记录核查。预热页展示每一天的目标、已接受、失败、错过、待发以及下次计划时间。

如果请求超时、worker 在发送中退出，或服务端返回可能无法确认结果的错误，记录会进入“待核销”。管理员先在 SendGrid 中核对，再选择“已接受”或“明确失败”。待核销期间对应收件人和通道容量保留，任务内后续发送暂停；系统不会自动重试这封邮件。暂停和恢复也不会重置 T0。

## 升级与备份

从旧版升级时，保留原数据库与上传文件。旧的“0–3 天库”“4–30 天库”记录、ID 和类型保留供历史任务引用；当前页面将它们按标签和邮箱统一展示，新计划按同一邮箱去重选择，不会把已发送或已预留的地址重新当作可用库存。已有任务、计划、占用关系、具名名单成员关系和发送历史继续保留。旧库名称不再出现在新建任务或收件人上传界面。

重复运行 VPS 安装脚本前，先保留运行中的数据库和 `.env`。安装器会在同步源码前创建带 WAL 内容的 SQLite 快照，并保护 `.env`、`backups/`、`data/`、`uploads/`、`logs/`。详细升级和回滚步骤见 `README_VPS.md`。验证新版本时使用模拟 SendGrid 请求，避免把测试邮件发送到真实地址。
