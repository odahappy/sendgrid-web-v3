# 预热系统方案审查

## 讨论流程

在改动源码前，20 位专项 agent 对现有 ZIP 做了只读检查，随后由独立项目经理 agent 验证整合方案。20 个岗位分别为：系统架构、前端 UI、数据库、调度、邮件合规、测试、收件人库存、API、worker 可靠性、安全、迁移、容量、产品交互、部署、维护、可观测性、前端可访问性、时间与时区、独立代码审阅、需求验收。

项目经理给原方案的结论为 **REVISE**，并批准了以下可直接实施的修订方案，之后才开始修改代码：

1. 标签、API 通道、代理共用一个后台管理页面，保留旧路由和页面锚点兼容。
2. 自定义预热任务独立于原有随机 30 天任务；首次点击启动时固定 UTC 锚点，每天为连续 86400 秒。
3. 现有两个收件人池可作为来源；新具名名单使用独立的 `warmup_named` 库类型及成员映射，避免被旧任务自动抽取。计划生成在一个写事务内核验归属、授权、去重、库存、模板与通道容量。
4. 自动模式均匀分布每天的数量；手动模式逐封按固定秒数安排。实际发送使用持久化间隔闸门与同任务单封在途限制；超出窗口的邮件标为错过，结果不明的邮件保留待人工核销。
5. 新旧任务共享通道自然日安全限额，但任务自己的 24 小时窗口独立计算。worker 给两类任务分配发送份额，防止一方长期占满轮询容量。
6. 升级时保留并备份生产 `.env` 与 SQLite 数据库；运行前后用模拟发送和既有测试验证。

## 验收结果

- 原有可靠性测试继续通过；新增测试覆盖滚动时间窗、零发送日、间隔临界值、名单去重与事务回滚、退订拦截、worker 并发、共享通道容量、重启/跨窗、HTTP 503/429/未知结果核销及旧新版任务交错。
- 预热名单上传 → 新建草稿 → 首次启动 → 渲染任务页面的 HTTP 流程使用临时测试数据库通过；没有调用真实 SendGrid。
- 生产安装脚本做了语法及重复安装数据保留检查。具体运行方式与边界见 `WARMUP_GUIDE.md`。
